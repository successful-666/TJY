# Car_Robot 固件架构设计

最后更新：2026-09-11

## 一、目标

主控板作为**协议网关**：上位机通过以太网 TCP 下发指令，固件翻译成 CAN / RS485 报文发给电机，
电机的反馈再回传给上位机。

```
 上位机 (PC)
    │  TCP
    ▼
┌──────────────────────────────────┐
│ Car_Robot (STM32F407 + FreeRTOS) │
└──────┬────────────────────┬──────┘
       │ CAN 1 (1 Mbps)     │ RS485 (USART2)
       ▼                    ▼
   DM3519 × N            Y42 × M
```

## 二、分层结构

```
code/
├── Core/        CubeMX 生成，除 USER CODE 段外不手改
├── Midwares 等  LwIP / FreeRTOS / HAL（第三方）
├── LWIP/        CubeMX 生成的网口适配（USER CODE 段内可改）
│
├── App/         应用层：编排、上位机协议、日志
│   ├── app.c/h        唯一启动入口 App_Init()
│   ├── app_eth.c/h    TCP 服务
│   ├── proto.c/h      上位机帧格式（纯逻辑）
│   └── log.c/h        线程安全日志
│
├── Service/     业务层：把"命令"变成"设备动作"
│   ├── svc_can.c/h    CAN 收发服务（队列 + 任务 + 自愈）
│   └── svc_motor.c/h  电机业务（状态缓存 + 在线检测）
│
├── Device/      设备层：协议编解码（纯逻辑，零硬件依赖）
│   └── dm3519.c/h     达妙 DM3519 CAN 协议
│
└── BSP/         驱动层：唯一的 HAL 接触点
    └── bsp_can.c/h    CAN 外设封装
```

**依赖方向严格单向下行**：

```
App  →  Service  →  Device  →  BSP  →  HAL
```

- `Device` 层不 include 任何 HAL / FreeRTOS 头文件（只依赖 `CAN_Frame_t` 这个数据类型），
  因此可以拿到 PC 上做单元测试
- `BSP` 是唯一直接读写 CAN 寄存器 / 调用 `HAL_CAN_*` 的地方
- `Service` 不解析字节，`Device` 不发送帧，职责单一

## 四、数据流

### 下行（上位机 → 电机）

```
TCP 帧 → proto 解析 → 业务判定 → SvcMotor_DmSetSpeedRpm()
       → 组 DM3519 帧 → SvcCan_Send()（入队，立即返回）
       → CanTx 任务取出 → BSP_CAN_Send() → 邮箱 → 总线
```

**关键点**：`SvcCan_Send()` 只入队、不等待。TCP 任务永远不会因为 CAN 总线忙而卡住。

### 上行（电机 → 上位机）

```
总线 → CAN 中断 → 排空硬件 FIFO → osMessageQueuePut（0 超时）
     → CanRx 任务取出 → SvcMotor_OnCanFrame() → 更新状态缓存
     → 上位机轮询（发查询命令，从缓存读）
```

**当前采用轮询上报**：电机状态缓存在 Service 层，上位机按自己的节奏查询。
这样 TCP 会话任务不需要支持"异步推送"，避免了一个客户端连着不放就堵住推送的问题。
后续若需要周期性主动上报，再引入独立的上报队列与发送任务。

## 五、健壮性设计

相对参考工程 `Frame_work`，本移植做了以下增强：

| 项目 | 参考工程 | 本工程 |
|---|---|---|
| CAN bus-off | 不处理 | `BSP_CAN_RecoverBusOff()` 周期巡检 + 自动恢复 |
| 中断工作量 | 一次中断排空整个 FIFO | 上限 16 帧，防止异常时长时间占用中断 |
| 队列满 | 静默丢包 | 计数 `rx_drop_count`，周期日志告警 |
| 发送失败 | 无上限重试 | 最多重试 20 次后丢弃并记账，避免任务永久挂住 |
| HAL 返回值 | 部分未检查 | 全部检查，失败回滚 |
| 初始化顺序 | 隐式 | `App_Init()` 显式按依赖顺序装配 |
| 状态跳变日志 | 无 | 只在 online / error_code 跳变时打印，避免刷屏 |
| 堆 | — | 32KB，静态队列元素 + 启动期一次性分配 |
| 栈溢出 | 无检测 | `configCHECK_FOR_STACK_OVERFLOW = 2` + 钩子 |
| 内存分配失败 | 无检测 | `configUSE_MALLOC_FAILED_HOOK = 1` + 钩子 |

### 为什么 bus-off 必须软件恢复

当前 CubeMX 配置里 `AutoBusOff = DISABLE`。此时一旦总线出现严重错误（例如波特率不匹配、
短路），bxCAN 会停在 bus-off 状态**不再发送也不再接收**，而且没有任何中断通知。

软件恢复流程（`BSP_CAN_RecoverBusOff()`）：

1. 读 `CAN_ESR` 的 `BOFF` 位判断是否处于 bus-off
2. `HAL_CAN_Stop()` —— 进入初始化模式，硬件自动清除 BOFF
3. `HAL_CAN_Start()` —— 退出初始化模式，重新参与总线
4. 重新激活 FIFO0 接收通知

这条路径由 CanRx 任务在等待接收队列超时后（每 100ms）执行一次。

### 建议在 CubeMX 里同步修改

【待办】`CAN1` 的 `AutoBusOff` 和 `AutoRetransmission` 建议都改为 `ENABLE`：

- `AutoRetransmission`：报文发送失败时硬件自动重发，是 CAN 的常规行为
- `AutoBusOff`：硬件自动从 bus-off 恢复，比软件巡检更及时

两者都开之后，上面的软件恢复逻辑仍保留作为兜底，不冲突。

## 六、与参考工程的差异

| 参考工程 `Frame_work` | 本工程 | 原因 |
|---|---|---|
| 裸机协作式调度 `Scheduler_Run()` | FreeRTOS 任务 | 以太网 + LwIP 必须跑在 RTOS 上 |
| 自研 `Queue_t` | `osMessageQueue` | 用 RTOS 原语，避免重复造轮子 |
| 自研 `Event` 发布订阅 | 直接回调 + 后续按需引入 | 单消费者场景下事件中心是过度设计 |
| `Event_Publish` 同步分发 | 队列解耦 | 避免生产者在消费者处理期间被阻塞 |
| `can_service` 依赖 `app_events` | Service 不依赖 App | 修正跨层反向依赖 |
| `servo_motor` | 已移除 | 用户确认不再使用舵机 |
| `crc.c` (CRC8/CRC16) | 未移植 | 当前 TCP 协议自带 CRC16，485 待 Y42 资料定 |

保留沿用的部分：

- 五层分层思想与命名规范
- `CAN_Frame_t` 数据结构
- `dm3519.c` 的协议实现（字段定义与位分布**完全未改**，只增强了健壮性）
- BSP 只做搬运、不解析协议的原则
